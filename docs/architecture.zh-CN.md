# 各部分怎样配合

[English](architecture.md)

本页帮助维护者快速理解工具结构。初次使用者可以先完成[入门指南](getting-started.zh-CN.md)
中的示例编译，之后再阅读本页。

## 常规流程

```text
foundation.toml
      |
      v
编译和测试 --------> 发布归档 + 校验文件
      |                         |
      v                         v
GitHub 自动检查             安装发布版本
                                |
                                v
                            激活并验证
                                |
                         失败：恢复旧版本
                         中断：执行 recover
```

`foundation.toml` 提供项目自己的名称和命令。Python 工具读取该文件，对每个生成项目
执行相同的通用流程。

## 工具负责什么

- 创建初始目录和示例文件；
- 检查项目设置是否指向有效文件和目标；
- 运行固定版本的源码检查工具；
- 创建和验证发布归档；
- 记录生成发布包的源码提交和依赖；
- 在已安装版本之间切换，并保存事务记录；
- 创建可验证的备份和运维记录。

## 应用团队负责什么

- 业务行为、API 和数据存储；
- 有实际意义的测试和健康检查；
- 依赖选择和 lockfile 更新；
- 生产主机、凭据和访问规则；
- 数据迁移、容量、可用性和灾难恢复计划；
- 是否发布或回滚的最终决定。

这个边界是有意设计的：通用工具可以检查健康命令是否成功，但只有应用团队知道“健康”
对当前业务究竟意味着什么。

## 自动检查

Pull request 会运行速度较快的常规检查，包括编译、测试、源码格式、编译器告警、部分
代码分析和覆盖率。较慢的检查会定时运行或手动启动，检查 Docker 文件、文档和重复编译
等内容。

所有设置都保存在仓库中。检查失败后，workflow 不会自动降低限制。

## 发布包内容

发布包只包含明确声明的运行程序和文件，另外还包含：

- 记录每个文件、大小和 SHA-256 的 manifest；
- 源码提交和编译信息；
- SPDX 软件清单；
- 运行时内容的稳定摘要。

验证程序会拒绝额外文件、缺失文件、文件模式变化、不安全的归档路径和错误校验值。

## 部署状态

默认目录把不可修改的发布文件与会变化的事务记录分开：

```text
/opt/<project>/releases/<deployment-id>/
/opt/<project>/deployments/<deployment-id>/record.json
/opt/<project>/current -> deployments/<deployment-id>
/opt/<project>/previous -> deployments/<deployment-id>
/var/lib/<project>/transactions/<transaction-id>/record.json
```

同一时间只有一个部署命令可以修改状态，版本指向会一次性切换。候选版本检查失败时会恢复
旧版本；进程中途停止时，后续激活会被阻止，直到运维人员执行 `deploy recover`。

该目录结构有意不包含应用数据，应用数据必须单独管理。
